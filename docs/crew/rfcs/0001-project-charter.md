# RFC 0001：knowledge-crew 專案章程

- 狀態：Accepted
- 日期：2026-11-19
- 相關：#1

## 摘要

knowledge-crew 是帶領 AI 員工的工作平台：交辦、驗收，信任隨驗收長出來。人在平台上把工作交辦給 AI 員工、驗收結果；每次驗收都留下紀錄，平台依紀錄建議哪些工作可以少看，放不放寬由人決定。

knowledge-crew 不是 CrewAI 框架的範例或延伸；名稱中的 crew 指「一起工作的 AI 員工」。

## 問題與使用者

### 問題

AI 能做的工作越來越多，但人不知道該信它多少：每項都逐一看會累，放太鬆會漏掉錯誤，而且信任沒有紀錄可依據，只能憑印象。

### 使用者

1. **第一個使用者：專案擁有者自己的 AI 開發流程。** 以 GitHub Issue 派工給 coding agent、在 PR 驗收。已有一個既有專案的回顧資料：258 個已合併 PR，77% 第一次就通過；59 個修正中，16 個只是測試或 rebase，7 個是設計判斷。資料現成、回饋最快。
2. **之後：個人經營者與知識平台操作者。** 把同一套骨架延伸到業務工作（例如 LINE、Email 的回覆與整理）。

### 結果錯了的後果

- **派工出錯**（開錯 Issue、加錯標籤）：浪費 agent 的額度、在 repo 留下雜訊，但可以回復。
- **信任建議錯了**（讓人少看了該看的東西）：錯誤的 PR 被合併。這是最嚴重的後果，因此下方「必要功能」不能拿掉。

## 提案

### 核心概念

- **AI 員工**：可設定的 AI 執行者。資料結構保留「執行者類型」欄位；先只支援平台自己可設定、可以做事的執行者。
- **交辦**：一句話交辦。在開發流程中，交辦＝在對應的 repo 開 Issue、加上派工標籤；工作狀態從 GitHub 讀回。
- **驗收**：驗收面板顯示員工標出的「要看的重點」、自動檢查結果，全文預設收起。
- **退回原因三選一**：
  - 做錯了（影響信任）：畫面不符、bug、內容錯誤、安全問題。
  - 我想要不一樣的做法（不影響信任）：設計判斷。
  - 流程上的小問題（不影響信任）：測試、rebase。
- **信任紀錄**：工作類型 × 退回原因 × 誰決定。

### 必要功能（防止過度信任，不能拿掉）

- 員工主動標出「要看的重點」（開發流程中先從 coding agent PR 描述的「人工待辦」接）。
- 一次「做錯了」，該類工作就自動改回逐項看。
- 「少看」的建議要人同意，而且可以隨時收回。

頭像、暱稱等「同事感」可能讓人過度信任，由上面三項防範。

### 畫面

以個人經營者的互動為主：

- 今天、員工、交辦、工作與驗收、信任（最近 10 次驗收以圓點表示）。
- 「工作帳本」歷史紀錄頁：需要追查「誰改了什麼、為什麼」時才打開。

### 兩個 repo 的邊界

| 公開 repo `knowledge-crew` | 私人 repo `knowledge-crew-ops` |
| --- | --- |
| 畫面：今天、員工、交辦、工作與驗收、信任 | 真正的資料庫與 migration |
| 虛構資料的 demo（瀏覽器內資料庫） | 串接 GitHub 與執行者的寫入 |
| 概念與資料格式 | 登入、權限、多客戶隔離 |
| 設計文件、RFC、ADR | 信任與建議規則的實際參數 |
| | 任何真實紀錄 |

- 原則：公開的是「看起來怎樣、概念是什麼」；私人的是「真的連到誰、存了什麼、規則怎麼調」。
- 私人 repo 等第 1 階段要實際派工時才開，以公開 repo 為上游。

### 資料

平台以自己的資料庫為主，GitHub 只是串接來源之一。資料庫與部署的技術選型寫在 ADR。

## 不做什麼

公開 repo 一律不放：真實資料、串接設定、規則的實際參數、任何真實紀錄。

第一版不做：

- 真實資料與登入（第 0 階段只用虛構資料）。
- 串接其他廠牌的 AI（例如 LINE 的 AI agent）；只在資料結構保留「執行者類型」。
- 時間估計（例如「大約 6 分鐘」）；要先累積資料。
- 業務工作的自訂自動檢查；開發流程中的自動檢查就是 CI。
- 在雲端直接執行 AI 員工；需要 API 金鑰、按用量付費，牽涉成本與金鑰管理。
- 取代 GitHub 上的審查；審查仍在 GitHub 與決策中心進行。

## 階段與門檻

每個階段一個 Epic，看板以 Phase 欄位標示。

| 階段 | 內容 | 門檻 |
| --- | --- | --- |
| 0. 公開 demo | 五個畫面（今天、員工、交辦、工作與驗收、信任）與工作帳本，使用虛構資料 | 決定者能用 demo 走完一次「交辦 → 驗收 → 退回 → 信任變化」，並確認方向 |
| 1. 員工與派工 | 開私人 repo；在平台交辦＝在 repo 開 Issue、加標籤；狀態從 GitHub 讀回；執行仍由既有的 coding agent 負責 | 連續 10 張經平台派工的真實 Issue，狀態都正確讀回 |
| 2. 紀錄與報表 | 第 1 階段累積的事件整理成信任紀錄；退回原因三選一；補匯入既有專案的 258 筆歷史 PR | 能依工作類型看到信任紀錄 |
| 3. 建議與放手 | 依紀錄建議審查程度、提出升級建議（例如只改測試的修正簡化複審）；規則改變仍走各 repo 的 Issue 與 `## 決定` | 至少一條建議經決定者同意後實際採用 |
| 4. 外部執行者 | 開放接口，讓其他平台的 AI 回報工作 | 第 3 階段後再定 |

### 怎麼算成功

半年內，決定者自己的 repo 有一半以上的 PR 經平台交辦，而且至少有一類工作依信任紀錄放寬了審查。

## 待決問題

- 中文名稱。
- 資料庫代管廠商與平台部署位置（ADR 0001）。

## 修訂

### 2026-11-19：建立在 knowledge-kit 之上（#5、ADR 0002）

- **產品定位**：knowledge-crew 以 [knowledge-kit](https://github.com/BenTsai0212/knowledge-kit) 為上游，建立在它之上，保留它的全部功能（知識庫、問答、檢索、文件解析、圖譜、評測等），再加上 AI 員工的交辦、驗收與信任。knowledge-kit 的改進持續同步進來（ADR 0002）。
- **AI 員工的工作範圍**：先做開發流程（「使用者」第 1 項）；基本功能完成後，再決定是否擴及知識庫中的工作。
- **三個 repo**：

  | repo | 角色 |
  | --- | --- |
  | `knowledge-kit`（公開） | 上游：知識庫產品 |
  | `knowledge-crew`（公開） | 本 repo：knowledge-kit 的全部功能，加上 AI 員工的畫面、概念與 demo |
  | `knowledge-crew-ops`（私人） | 不變：真正的資料庫、串接、規則參數與任何真實紀錄 |

- **資料**：資料庫做法沿用 knowledge-kit（PGlite、RLS、migration）。
- **第 0 階段**：demo 是 knowledge-kit 的現有功能，加上五個畫面與工作帳本；AI 員工相關的資料仍只用虛構資料。門檻不變。
- **伺服器端功能**：knowledge-kit 的 Worker（模型呼叫、邀請碼、費用上限）隨匯入保留；是否在 knowledge-crew 的 demo 啟用，另行決定。
