# 交件全文的格式

交件的全文（`client/crew/demo.json` 的 `works[].body`，資料庫的 `crew.works.body`）的結構，以及「要看的重點」在全文中的標記。依 #65 的 `## 決定`；解析函式是 `app/src/crew/work/body.ts` 的 `parseWorkBody()`。

- 全文仍是一段文字，**不改資料結構**：`works.body` 是 `text`，`work_points` 不變，migration 不動。
- 每種語言各有一份完整的全文（`LocalizedText`），資料庫只存預設語言，畫面以 `demoText()` 換成目前語言。
- `demo.json` 裡每種語言的全文寫成一行字串，換行寫成 `\n`。

## 區塊

一行以 `@@ ` 開頭時，開始一個新區塊，到下一個標頭行或全文結尾為止是區塊的內容。內容的前後空行去掉，中間的空行保留；內容可以是空的（空白欄位）。

```text
@@ <鍵> [屬性] [屬性] | <名稱>
```

- **鍵**：不含空白，與 `changes[].path` 的寫法**完全相同**（`reply/p2`、`post/title`、`kb/<條目>#<欄位>`、程式修改的檔案路徑）。同一份全文的鍵不可重複。
- **屬性**：可省略，可以有多個。

  | 屬性 | 意思 |
  | --- | --- |
  | `[required]` | 必填欄位（知識庫條目）；空白的必填欄位是 `[required]` 且內容空白 |
  | `[added]`、`[modified]` | 程式修改的檔案是新增或修改（兩者擇一） |
  | `[point N]` | 整個區塊是第 N 個重點（見下文） |

- **名稱**：可省略。只用在內容本身有名稱的區塊，也就是知識庫的條目名稱與欄位名稱（例如「負責部門」）。回信段落的名稱（「問候」「第 2 段」）與貼文各部分的名稱是介面文字，由畫面依鍵換成 `client/i18n/crew/` 的文字，不寫在全文裡。

交件類型由交辦的工作類型決定，全文裡不另外寫。每種交件的鍵（依畫面由上到下的順序）：

| 交件 | 鍵 | 說明 |
| --- | --- | --- |
| 回信 | `reply/to`、`reply/subject`、`reply/greeting`、`reply/p1`…`reply/pN`、`reply/closing`、`reply/attachment` | 寄給、主旨、段落；段落是否「已修改」從 `changes` 推得 |
| 貼文 | `post/account`、`post/title`、`post/body`、`post/hashtags`、`post/image`、`post/image-alt` | 帳號列、標題、內文、標籤、圖片與圖片說明 |
| 知識庫條目 | `kb/<條目>`（名稱是條目名稱，內容可空）、`kb/<條目>#<欄位>`（名稱是欄位名稱） | 欄位依出現的順序；`changes[].path` 的 `kb/<條目>` 對到條目區塊 |
| 程式修改 | `<檔案路徑>`（`[added]` 或 `[modified]`，內容是一句說明）、`pr/description` | PR 描述預設收起由畫面決定 |

第一個標頭行之前不能有內容（空行除外）。知識庫條目的例子：`@@ kb/pre-orders#owner [required] [point 1] | 負責部門`。

## 重點的標記

`N` 是 `points` 的順序（從 1 開始，等於 `work_points.ordinal` 與畫面上的重點編號）。

- **詞句**：在區塊內容中以 `〔N〕` 與 `〔/N〕` 包住，例如 `預計在〔1〕12 月第 2 週〔/1〕到貨`。標記可以跨行，但不可跨區塊。
- **整個區塊**：在標頭行寫 `[point N]`，可以用在空白欄位（沒有文字可以包）。
- **一個重點跨兩段**：在兩個區塊各標一次同一個 `N`。
- **一段有兩個重點**：同一個區塊內用不同的 `N`；兩個範圍不可重疊或巢狀。
- 同一個 `N` 可以同時有 `[point N]` 與其他區塊的行內標記。
- 只有 `〔` 後接數字（可加 `/`）再接 `〕` 的寫法是標記；其他的 `〔…〕` 是一般文字。

## 例

回信（zh-TW）：

```text
@@ reply/to
林小姐
@@ reply/subject
預購保溫瓶的到貨時間
@@ reply/greeting
林小姐您好，謝謝您的來信。
@@ reply/p2
您預購的保溫瓶預計在〔1〕12 月第 2 週〔/1〕到貨，出貨後會再寄送通知。
@@ reply/closing
運費部分，〔2〕單筆滿 NT$ 1,000 免運，未滿酌收運費 NT$ 80〔/2〕。如有其他問題歡迎再與我們聯繫。
```

## 兩種語言

兩種語言的全文必須對齊的部分：區塊的鍵與順序、每個區塊的屬性、每個區塊出現的重點編號。可以不同的部分：名稱、內容文字、標記包住的詞句（例如 zh-TW「12 月第 2 週」、en「the second week of December」）。

## 解析結果與退回

`parseWorkBody(body, pointCount)` 回傳 `structured`（有任何標頭行）、每個區塊的鍵／名稱／屬性／去掉標記後的文字與行內位置、每個重點的位置清單（沒有 `range` 表示整個區塊），以及錯誤（代碼與行號，代碼的意思見 `body.ts` 的 `BodyErrorCode`；給人看的文字由呼叫端決定）。

- **沒有任何標頭行**（舊格式的一行摘要、由沒有改寫的模擬回覆產生的交件）：一個沒有鍵的區塊，內容原樣，不處理 `〔N〕`；重點只列在重點卡。
- **有標頭但寫錯**：`errors` 不是空的；文字仍去掉認得的標記，不合格的標記不列入位置。畫面退回顯示純文字、不畫底線。
- `toPlainText(body)`：給還沒有結構化呈現的畫面使用，區塊之間空一行，去掉標頭、名稱與標記，略過空白區塊；舊格式原樣回傳。

## `demo.json` 的檢查

`app/src/crew/demo/validate.ts` 對每件交件與模擬回覆的全文檢查（有錯時 seed 不寫入）：

- 有標頭行的全文：解析沒有錯誤；每個重點（1…`points.length`）至少有一個位置；每個 `changes[].path` 都是某個區塊的鍵；區塊的鍵符合交辦的工作類型（`support` 是 `reply/`、`content` 是 `post/`、`knowledge` 是 `kb/`、`dev` 是其他；其他工作類型不檢查）。
- 兩種語言要嘛都有結構、要嘛都沒有；都有時依上面「兩種語言」對齊。
- 等待驗收的交件（最後一輪沒有驗收）必須是有結構的全文。
- 沒有標頭行的歷史交件與模擬回覆不檢查位置。

改寫成有結構的全文：待驗收的 s14、c11、k13、j06，每位員工最近驗收的 s13、c10、k12、j05，以及八則模擬回覆；其他交件維持一行摘要（#65 的 `## 決定` 3）。驗收面板 v3 之前，畫面以 `toPlainText()` 顯示全文。

## PR 描述轉成的交件

第 1 階段由 GitHub 讀回的 PR 轉成程式修改的交件（#112，#108 的 `## 決定` 第 5 點）；轉換函式是 `app/src/crew/github/pr.ts` 的 `prToWork()` 與 `parseManualTodos()`，輸入是 PR 描述與 GitHub「列出 PR 的檔案」回應的形狀（`github/types.ts` 的 `GitHubPrFile`）。

**要看的重點**取自 PR 描述的 `## 人工待辦`（格式見 `.github/pull_request_template.md`）：

- 每個核取方塊是一個重點，順序就是編號；勾選與否都算，另記在 `checked`。
- 在 `合併前：`、`合併後：` 小標下的核取方塊，重點文字寫成 `合併前：<文字>`；核取方塊下縮排的下一行接在同一個重點後面。
- 寫「無」（可加 `- ` 或句號，也可以寫在小標後面，例如 `合併後：無`）、區塊空白，或只有範本留下的空核取方塊：**沒有重點**。
- **讀不到人工待辦**：找不到 `## 人工待辦`（程式碼區塊與 HTML 註解中的不算）、出現兩次，或區塊內有核取方塊、小標、「無」以外的內容（同一個小標下同時有「無」與核取方塊也是）。這時不猜，回傳 `ok: false` 與原因；沒有重點不等於沒有要看的事，畫面要請人到 GitHub 看 PR 描述。

**交件全文**：

- 變更的檔案依輸入順序各是一個區塊：`added` 寫 `[added]`；`removed` 不加屬性；其他（`modified`、`renamed` 等）寫 `[modified]`。GitHub 沒有每個檔案的說明，所以內容是空的。
- 路徑含空白、或與 `pr/description` 相同的檔案不能當區塊的鍵，不寫進全文，列在 `omittedFiles`；重複的路徑只算一次。
- 最後是 `pr/description`：PR 描述去掉 HTML 註解與讀得到的人工待辦（讀不到時原文保留），連續空行併成一行。
- PR 描述中以 `@@` 開頭的行（例如 diff 的 hunk 標頭）與 `〔N〕`、`〔/N〕` 的寫法，前面加零寬空白（U+200B），不會被讀成標頭行或重點標記；畫面上看起來不變。
- **變更**（`work_changes`）：每個寫進全文的檔案一筆，說明是增減的行數 `+<增> -<減>`，GitHub 沒有給行數時是空字串。
