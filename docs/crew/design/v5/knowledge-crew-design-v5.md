# knowledge-crew 設計規格 v5：少字版

- 狀態：方向與用詞已由決定者同意（2026-11-26）
- 取代：設計規格 v4 的用詞、AI 員工的子頁結構與文字；v4 的外框、元件、顏色、可近用性規則照舊
- 設計稿：`screens/` 的 18 個 HTML（桌機與手機同一份）、`img/` 的截圖

---

## 1. 為什麼改

v4 統一了視覺，但每個畫面還是要讀 400～1,000 字，而且用詞是從系統的角度取的（最明顯的是「信任」）。決定者在 2026-11-26 同意四件事：

1. 可以改用詞（包括 RFC、ADR 與介面文字）。
2. 「信任」改叫 **審查方式**。
3. 「信任」併進員工頁，AI 員工的子頁從 6 個減成 4 個。
4. 字數有預算；頁面設計能把價值講清楚的，就不用文字解釋。

## 3. 結構

**AI 員工的 4 個子頁**

| 子頁 | 內容 | 原本在哪 |
| --- | --- | --- |
| 工作 | 待驗收清單與驗收面板；「清單｜看板」切換 | 工作與驗收、總覽 |
| 員工 | 每位員工的審查方式、最近 10 次、守則 | 員工、信任（每類工作的卡） |
| 交辦 | 交辦表單、最近交辦 | 交辦 |
| 紀錄 | 事件（新到舊）；「看統計」切換成統計表 | 工作帳本、信任的總表 |

每位 AI 員工只負責一種工作，所以「這類工作要看多細」就是「這位員工要看多細」，放在員工卡上最直接。

**首頁**：今天的工作（前 5 件）、等你決定、最近的變化、問知識庫。「最近新增的文件」移到時間軸（時間軸本來就是新的在上面）；「問過的問題」「最近看過」沒有內容時不顯示。

## 4. 寫作規則

1. **一個畫面只回答一個問題**：驗收是「可以通過嗎？要確認哪裡？」，員工是「要看多細？」。
2. **狀態用圖示、徽章表達**：✕／✓ 系統檢查標籤、10 個圓點、「全部看｜只看標記處」開關。不寫「通過 9・做錯了 1・其他退回 0」這類句子。
3. **說明只放在「?」裡**，或第一次遇到時說一次。規則句不在多個畫面重複。
4. **列表只放和決定有關的**：標題、員工、一個最急的狀態。來源、編號、交件時間、輪次、優先放進「詳細」。
5. **字數預算**：首頁與驗收面板第一個畫面 200 字內（不含交件本文），員工卡每張 80 字內，按鈕 6 字內，「?」裡的說明 60 字內。
6. **員工標記的說明寫短**：「請你確認」的每一處 12 字內（例如「答應的到貨日期」），`demo.json` 的文字一起改。

**實測**（桌機 1280×900 第一個畫面，不含交件本文、左側清單與分頁）

| 畫面 | v4 | v5 |
| --- | --- | --- |
| 首頁 | 519 | 263 |
| 驗收・全部看 | 263 | 126 |
| 驗收・只看標記處 | 380 | 139 |
| 驗收・抽查 | 286 | 131 |
| 驗收・已通過後補記錯誤 | 350 | 114 |
| 員工＋審查方式（v4：員工＋信任） | 1,067 | 305（4 張卡，平均每張不到 80） |
| 紀錄（v4：工作帳本） | 437 | 278 |

首頁仍比預算多 63 字。再減的做法：「最近的變化」只放在鈴鐺打開的面板，首頁不列（第 8 節第 3 點）。

## 5. 和 v4 不同的元件

其他元件、顏色（含 `borderStrong`）、外框、可近用性規則都沿用 v4。

| 元件 | 規格 |
| --- | --- |
| 審查方式開關 | 兩格 pill：「全部看｜只看標記處」；目前的一格填色（全部看＝墨色、只看標記處＝`success`）。在員工卡上是**狀態顯示**，改變用旁邊的按鈕（改為只看標記處／改回全部看），避免誤觸 |
| 請你確認 | 標題「{{AI}} ○○ 請你確認 N 處」；每一處一列：墨色編號、說明（可點，交件中同編號加底線）、位置（小字）；守則一列「照守則：…」＋「?」看全文 |
| 系統檢查標籤 | pill：未通過＝`danger` 框＋✕＋粗體；通過＝勾＋`success` 字；檢查中＝`warning` 框 |
| 結論 | 一句，18px 粗體：「✕ 先別寄出：報價對不上」；系統檢查都通過時「✓ 系統檢查都通過」 |
| 詳細 | 文字按鈕，點了打開小面板，放來源、編號、交件時間、輪次、優先、到期日 |
| 「?」說明 | 18px 圓形按鈕，打開 60 字內的說明；Esc 關閉；用 `details/summary` 或按鈕＋`aria-expanded` |
| 相對期限 | 逾期 N 天（`danger`）、明天到期（`warning`）、N 天後到期；確切日期在「詳細」 |
| 清單／看板切換 | 兩格連結；目前的一格墨色底 |

**退回對話框**：標題「為什麼退回？」；三選一，選項下直接寫後果（做錯了：「Rowan 會改回全部看」，其他：「審查方式不變」）；給員工的意見；「記成守則，之後照做」；「錯在沒標記的地方」（只在做錯了時出現）。

**導覽 5 步**（文字更短）：今天的工作／驗收／退回／審查方式／收進知識庫。每步一句話、30 字內。

## 7. 不能動的規則：換了用詞之後

| 規則 | v5 的寫法 |
| --- | --- |
| 員工標出要看的重點 | 「○○ 請你確認 N 處」，在驗收面板最上面，交件中同編號標出 |
| 一次做錯了就改回 | 退回選項「做錯了・會改回全部看」；紀錄的「自動改回全部看」 |
| 改要人同意、可以收回 | 員工卡的「改為只看標記處」「改回全部看」按鈕；「?」說明 |
| 抽查不能關掉 | 徽章「抽查：這次全部看」，沒有關閉按鈕；「?」寫明不能關掉 |
| 退回原因三選一、標明影響 | 原本要求「影響信任」寫在選項上，改為直接寫後果「會改回全部看」／「審查方式不變」。**需要修訂設計規格 v3 第 6.2 節的寫法** |
| 員工自述與系統檢查分開 | 「請你確認」與「系統檢查」左右兩區，各有標題 |
| 補記錯誤不能撤回 | 對話框寫明「算一次做錯了，不能撤回」 |
| 黃色只代表出處、AI 標記、不懲罰、不排名、可近用性、雙語、虛構資料標示 | 照 v4 |

## 8. 要跟著改的地方

**文件**：RFC 0001（必要功能的用詞）、ADR 0007（守則：確認→採用）、ADR 0008（事後更正→補記錯誤、看重點→只看標記處）、設計規格 v3 第 6.2 節。建議另寫一份 ADR 記下這次的用詞與結構決定。

**程式與資料**：`client/i18n/crew/*.json` 與英文版、`app/src/crew/ui/sections.ts`（子頁）、`tour-steps.ts`、`client/crew/demo.json`（「要看的重點」的文字改短）、e2e 依文字找元件的測試。資料結構不變。

**還沒決定**
1. 首頁的「最近的變化」是否只放在鈴鐺裡（為了符合 200 字預算）。
2. 英文用詞（第 2 節）。
