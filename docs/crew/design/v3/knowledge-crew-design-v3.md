## 1. 背景與目標

**knowledge-crew 是帶領 AI 員工的工作平台：交辦、驗收，信任隨驗收長出來。**建立在 knowledge-kit 之上（ADR 0002），AI 員工是 knowledge-kit 側欄中的一個頁籤（ADR 0004），內有六個子頁。

- **公開原型的對象**：個人工作者與小公司，展示通用情境，不鎖定單一產業（RFC 0001 2026-11-21 修訂）。
- **虛構情境**：「範例公司」與四位 AI 員工：

  | AI 員工 | 工作類型 | 工作來源 | 交件 | demo 開始時的層級 |
  | --- | --- | --- | --- | --- |
  | Rowan（客服） | 客戶回覆 | 客服信箱 | 回信草稿 | 逐項看（10/09 同意少看，10/15 做錯了後自動改回） |
  | Sorrel（內容） | 貼文與商品介紹 | 官方社群帳號 | 貼文草稿 | 逐項看，有少看建議等人同意 |
  | Linden（文件） | 知識庫整理 | 公司知識庫 | 知識庫條目 | 少看（10/13 同意） |
  | Juniper（開發） | 網站與工具開發 | `example-org/company-site` | 程式修改（PR） | 逐項看（驗收 7 次，未達建議門檻） |

- **最大的風險是過度信任**。RFC 的三項必要功能不能拿掉，設計只能改呈現：
  1. 員工主動標出「要看的重點」。
  2. 一次「做錯了」，該類工作就自動改回逐項看。
  3. 「少看」的建議要人同意，而且可以隨時收回。
- **驗收的四條不能拿掉的呈現**（設計簡報 v2）：重點放最上面、不論層級；自動檢查一定看得到，未通過要明顯；逐項看時列出每項變更、少看時收成一行（重點與檢查照樣顯示）；驗收只有通過與退回，退回時選三種原因之一，只有「做錯了」影響信任。

## 2. 風格分析的結論（為什麼是這個方向）

**knowledge-kit 的底子**：「安靜、誠實、以出處為主角的閱讀工具」。

- 視覺「墨與螢光」：墨黑字、灰白底；藍色 `primary` 只代表可以操作；黃色 `mark` 只代表出處（ADR 0008，客戶不能改）。
- 三條原則：出處是主角；誠實的空白（虛線框、說明原因、給下一步，不用紅色、不搖晃）；動態只解釋因果。
- 語氣：白話短句、不用驚嘆號、不附和不稱讚、AI 不擬人（`docs/design.md`「AI 開口規則」）。

**和 knowledge-crew 目標的關係**：

- 呼應：「出處是主角」＝「要看的重點＋自動檢查」，都是先給依據再讓人判斷；「不懲罰」＝退回三選一；「誠實的空白」＝少看不能變成看不到。
- 落差（v3 要補的）：
  1. 現有的 AI 員工頁面回到「通用後台」的樣子：代碼直接顯示、未通過與通過幾乎一樣顯眼、各頁都是同樣的白卡片。
  2. 「信任隨驗收長出來」看不到「長出來」：層級改變的歷史在工作帳本，沒有和信任頁接起來。
  3. RFC 刻意選了「人名＋職務」，但畫面沒有任何提醒這是 AI，和 knowledge-kit「不擬人」有張力。
  4. 「待審（知識庫）」與「待驗收（AI 員工）」兩種待辦並排，用詞不一致。

**v3 方向**：以「墨與螢光」為底（方向 A），「今天」與驗收採收件匣的版面（方向 C），信任採帳本式的時間軸（方向 B）。不採用頭像與聊天式的「同事感」（方向 D），因為它正是 RFC 警告的過度信任來源。

## 3. 五個設計決定

| # | 決定 | 理由 | 和既有規則的關係 |
| --- | --- | --- | --- |
| 1 | 黃色證據色只代表出處；「要看的重點」用**墨色編號＋底線** | 證據色混用會讓「出處」失去意義 | 符合 ADR 0008，不需修訂 |
| 2 | 檢查未通過只用 `danger` 色的**文字、圖示、1px 細框**；不做整片紅底，`warning` 也不做大面積底色 | 不懲罰；輕重靠位置（放最上面）與措辭（「先別寄出」） | 符合 `docs/design.md` 的顏色用途與動態原則 |
| 3 | AI 員工一律呈現為**「AI」標記＋名字＋職務**；員工頁用職務圖示，不用頭像 | 保留 RFC 的人名＋職務，同時每次都提醒是 AI | 保留 RFC 決定；緩和與「不擬人」的張力 |
| 4 | 「今天」＝**收件匣**，依需要你的程度排序；驗收＝左清單右內容 | 個人經營者最熟悉讀信的版面；一眼知道先做什麼 | 新增；ADR 0004 的頁籤結構不變 |
| 5 | 「信任」＝**每類工作一條時間軸**：圓點＋層級帶＋誰在哪天改了層級 | 讓「信任隨驗收長出來」可以被看見，並且可追查 | 資料來自既有的驗收與層級決定，不改資料結構 |

**用詞**：AI 員工一律「驗收／通過／退回」；知識庫維持「審核／核准／退回」。側欄兩個數字分開（「待審」與「AI 員工」），不合併。

## 4. 視覺系統（沿用 `client/theme.json` Light）

### 顏色的用途

| token | 值 | 在 AI 員工畫面的用途 |
| --- | --- | --- |
| `background` | `#F5F6F3` | 整頁底色 |
| `surface` | `#FFFFFF` | 卡片、側欄、清單項目 |
| `surfaceRaised` | `#EDEFF2` | 收件匣的列、逐項看的層級帶、點選中的重點位置 |
| `text` | `#14171A` | 主要文字、重點編號、重點底線、「AI」標記框線 |
| `textMuted` | `#5B6470` | 次要文字、小標、日期、其他退回的虛線圓點 |
| `border` | `#DDE1E4` | 卡片框線、分隔 |
| `primary` | `#2340C8` | 只代表可以操作：主要按鈕（通過、交辦、同意少看）、連結、目前頁籤底線、選取的清單項目、「等你決定」列的框 |
| `success` | `#1A6E33` | 通過的圓點與勾、少看的層級徽章與層級帶（框線＋字，不填滿） |
| `warning` | `#9A3D00` | 檢查中（文字＋時鐘圖示，不做底色） |
| `danger` | `#B42318` | 未通過（文字＋✕ 圖示＋1px 框）、做錯了的 ×、空白的必填欄位（虛線框） |
| `mark` 系列 | — | **AI 員工畫面不使用**（只代表出處） |

### 字體、圓角、尺寸

- 內文 Inter＋Noto Sans TC，15/24；交件本文 16，行高 1.8～1.85（閱讀優先）。
- 等寬 JetBrains Mono：日期、數量、repo 與 PR 參照、「AI」標記。
- 圓角：small 6（標記、空白欄位）、medium 10（按鈕、清單列、重點）、large 16（卡片）、pill 999（徽章）。
- 觸控目標至少 44px；手機底部按鈕 48px。焦點框沿用 `:focus-visible` 2px `focus`。

### 元件

| 元件 | 規格 |
| --- | --- |
| **AI 標記** | 18px 高、1px `text` 框、4px 圓角、等寬字 10px「AI」；放在員工名字前。所有出現員工名字的地方都要有（清單、面板、信任、帳本、表單） |
| **層級徽章** | pill；逐項看＝`textMuted` 框＋`text` 字；少看＝`success` 框＋字。文字「目前層級：逐項看」或簡寫「逐項看」 |
| **結論列** | 驗收面板標題下方，以分隔線隔開：24px 圖示＋18px 粗體一句結論＋14px 說明。未通過時圖示與標題是 `danger` 色（「先別寄出：報價核對沒有通過」）；檢查中是 `warning` 色；沒有問題時不顯示 |
| **要看的重點** | 卡片內每點一列：22px 墨色實心圓編號＋重點文字＋13px `textMuted` 位置（「第 2 段」「『負責部門』欄位」）。可點選，點選後該列加 1px 墨色內框，交件內對應位置加 `surfaceRaised` 底 |
| **重點在內容中的標記** | 對應文字加 2px `text` 底線，後接 16px 墨色上標編號 |
| **自動檢查列** | 未通過：1px `danger` 框、✕ 圖示、名稱＋白話說明、右側粗體「未通過」；通過：無框、`success` 勾、右側「通過」；檢查中：`warning` 時鐘、「檢查中」 |
| **收件匣列** | `surfaceRaised` 底、12px 圓角：狀態圖示（✕／時鐘／箭頭）＋標題＋AI 標記與員工・交件・來源＋狀態一句＋層級徽章＋「開始驗收」。「等你決定」的列改為 `surface` 底＋1px `primary` 框 |
| **收起的區塊** | 1px 虛線框（`#A9B0B8`）、透明底、chevron 圖示＋「其他 3 個欄位已收起（少看）：適用範圍、付款方式、取消規則」；展開後文字改為「收起沒標重點的欄位」 |
| **空白的必填欄位** | 1px `danger` 虛線框＋「空白・必填」；少看時也不收起 |
| **信任時間軸** | 10 欄格線。第 1 列：層級改變的事件（左側 1px 墨線＋「10/13 你同意少看」）；第 2 列：圓點＋等寬日期；第 3 列：層級帶（逐項看＝`surfaceRaised` 底；少看＝`success` 框＋字；不足 10 次的空位＝虛線框「還沒有更多驗收」） |
| **圓點** | 通過＝`success` 實心圓；做錯了＝`danger` 粗體 ×；其他退回＝`textMuted` 虛線空心圓。每組圓點附 `aria-label` 摘要（例如「通過 9、做錯了 1」） |
| **退回原因** | 三個單選卡：「做錯了・影響信任」（「影響信任」用 `danger` 字）、「我想要不一樣的做法・不影響信任」、「流程上的小問題・不影響信任」；下方備註（選填）；「取消」與「確定退回」（墨色實心按鈕，不用紅色） |
| **職務圖示** | 員工頁 48px 方框（1px `text`、12px 圓角）內放線條圖示：客服＝信封、內容＝喇叭、文件＝書、開發＝程式符號 |

## 5. 版面與導覽

- **桌機**：沿用 knowledge-kit 的左側欄（220px：字標、首頁、問答、圖譜、時間軸、上傳、待審、AI 員工；底部「虛構資料・展示用權限」與身分卡）。AI 員工在側欄的數字是**待驗收件數**，與「待審」分開。
- 內容區：標題「AI 員工」＋「虛構資料」徽章，下方子頁籤（今天、員工、交辦、工作與驗收、信任、工作帳本），「工作與驗收」與「信任」帶數字（待驗收件數、待決定的少看建議數）。內容最大寬 1220px。
- **手機**：頂端列「AI 員工」＋「虛構資料」＋身分徽章；子頁改為可橫向滑動的按鈕列；底部分頁列（首頁、問答、圖譜、時間軸、更多），AI 員工從「更多」進入。驗收頁的通過與退回固定在底部。
- 寬度不足時，左右欄依序堆疊（清單在下、面板在上，沿用現行 #50 的順序）。

## 6. 每個畫面

### 6.1 今天（收件匣）——`screens/Today.html`、`screens/TodayMobile.html`

- 開頭「午安」（沿用 knowledge-kit 首頁的問候規則）＋一句總結：「4 件工作等你驗收，其中 2 件有檢查沒通過；1 個『少看』建議等你決定。」
- 收件匣依序分組，空的組不顯示：
  1. **先處理・有檢查沒通過**：Rowan「詢問預購商品的到貨日」（報價核對未通過）、Linden「整理預購商品的說明」（必填欄位未通過）。
  2. **待驗收**：Sorrel「冬季限定組合的介紹」（連結檢查中・字數通過）、Juniper「常見問題頁的搜尋」（自動測試檢查中）。
  3. **等你決定**：「Sorrel 的『貼文與商品介紹』可以改成少看嗎？」→「到信任看紀錄」（不在今天直接同意，決定一律在信任頁做，避免順手放寬）。
  4. **進行中**：空的時候是虛線框「目前沒有進行中的交辦。交辦新工作」。
- 右側「信任一覽」：四類工作各一行，含最近 10 次圓點、層級徽章、最近一次層級事件；連到信任頁。
- 只有第一列的「開始驗收」是主要按鈕，其他是次要按鈕。

### 6.2 工作與驗收（逐項看）——`screens/Review.html`、`screens/ReviewMobile.html`

由上到下（四種交件共用同一套骨架）：

1. **標題卡**：來源與編號（「客服信箱・來信 1054」）、層級徽章、標題、「AI Rowan（客服）交的回信草稿・第 1 輪・11/17 11:00」、結論列。
2. **重點＋自動檢查**：兩張卡並排（窄螢幕堆疊）。
3. **交件本身**，以原本的樣子呈現：
   - 回信：寄給、主旨、段落；左側 96px 欄位標示段落名稱，修改過的段落加「已修改：說明到貨週」。
   - 貼文：帳號列、標題、內文、標籤、圖片與圖片說明（v2 Sorrel 畫板的版面，顏色依本文件第 3 節）。
   - 知識庫條目：條目名稱＋欄位清單（見 6.3）。
   - 程式修改：檔案清單（等寬路徑＋新增／修改＋一句說明），PR 描述全文預設收起，連到 GitHub 看差異；「通過只記錄驗收；合併在 GitHub 進行」（v2 Juniper 畫板的版面）。
4. **變更**：逐項看時在內容左側逐段標示，並在底部一行列出（「變更 2 項：第 2 段・結尾」）。
5. **決定列**：「這封信可以寄出嗎？」（貼文：「這篇可以貼出嗎？」；條目：「這則條目可以加進知識庫嗎？」；程式：「這份修改可以通過嗎？」）＋退回＋通過。

互動：點重點 → 內容中對應位置加底色、重點列加框，再點一次取消；按「退回」→ 展開退回原因（6.1 元件），預設不選原因以外的動作；「確定退回」才寫入。

### 6.3 工作與驗收（少看）——`screens/ReviewLight.html`

- 標題卡、結論列同 6.2（「先別加進知識庫：必填欄位沒有通過」「『生效日期』是空的。Linden 另外標了 2 個重點。」）。
- **為什麼是少看**（`success` 1px 框、盾牌圖示）：「你在 10/13 同意的；Linden 的『知識庫整理』最近 10 次沒有做錯。收起的只有沒標重點的欄位與變更。重點、檢查、空白欄位照樣顯示；一次『做錯了』就自動改回逐項看。」＋「看信任紀錄」。
- 條目欄位：有重點的欄位（負責部門、到貨時間）與空白欄位（生效日期）一律顯示；其他欄位收進虛線框，可展開。
- 變更收成一行：「變更 2 項已收起（少看）：新增條目、負責部門　逐項列出」。

### 6.4 信任（時間軸）——`screens/Trust.html`

- 標題「信任隨驗收長出來」、說明、圖例（通過／做錯了（影響信任）／其他退回（不影響））。

## 7. 用詞

### 統一的詞

| 概念 | 用詞 | 不用 |
| --- | --- | --- |
| 人對 AI 交件的判斷 | 驗收、通過、退回 | 審核、核准（保留給知識庫） |
| 信任層級 | 逐項看、少看 | 信任度高低、自動通過 |
| 層級的改變 | 同意少看、收回少看、因做錯了改回逐項看 | 升級、降級、懲罰 |
| 退回原因 | 做錯了／我想要不一樣的做法／流程上的小問題 | 錯誤、駁回 |
| 檢查狀態 | 通過／未通過／檢查中 | 執行中（改為「檢查中」）、pass／fail |
| 交件的稱呼 | 回信草稿、貼文草稿、知識庫條目、程式修改（PR） | 工作成果、output |
| 決定列的問句 | 這封信可以寄出嗎？／這篇可以貼出嗎？／這則條目可以加進知識庫嗎？／這份修改可以通過嗎？ | 確認送出？ |

語氣沿用 knowledge-kit：白話短句、不用驚嘆號、不稱讚；結論用「先別寄出：○○沒有通過」這類直接說明，不用「錯誤！」。

## 8. 資料與限制

- **不改資料結構**。畫面上的每個欄位都對應 `client/crew/demo.json` 既有的資料：標題、來源與外部編號、員工、工作類型、輪次、摘要、全文、要看的重點、自動檢查（名稱＋結果）、變更（位置＋說明）、驗收結果與原因、層級決定。
- **重點標到內容中的位置**：現在的資料只有重點的文字。要做到 6.2 的標記，需要員工在全文中加上標記（例如〔1〕…〔/1〕），不改結構但改變全文的寫法，**需要決定**。沒有標記時，重點只列在重點卡，內容不加底線。
- **檢查未通過的位置**：資料只存名稱與結果，畫面不宣稱「哪裡」未通過。空白的必填欄位是從內容本身看得出來的，所以可以標。
- **虛構範例內容**（不在 `demo.json`，實作時換成資料）：回信全文與「林小姐」、「12 月第 2 週」「單筆滿 NT$ 1,000 免運，未滿酌收運費 NT$ 80」；貼文全文、NT$ 1,580、省 15%、限量 300 組、12/1～12/31；條目欄位內容、「電商營運組」、生效日期為空。
- **照 `demo.json` 的資料**：所有驗收日期與結果、層級決定（Rowan 10/09 同意、10/15 自動改回；Linden 10/13 同意）、驗收次數、待驗收的四件、工作帳本的事件。
- 介面文字一律放在 `client/i18n/crew/<畫面>.<語言>.json`，元件不寫死文字（AGENTS.md 硬規則）；英文版要另外對照。

## 9. 和現有實作的差異（建議拆成的 Issue）

依「一張 Issue 一個 PR、400 行內」拆：

1. **共用元件**：AI 標記、層級徽章、結論列、自動檢查列（未通過的細框與圖示）、收起的區塊；「執行中」改「檢查中」。
2. **代碼的白話對照**：檢查名稱與變更位置的翻譯檔與轉換函式（第 7 節），畫面不再出現代碼。
3. **驗收面板 v3**：結論列、重點卡（可點選）、交件依類型呈現（回信、貼文、條目、程式）、決定列的問句、退回原因的「影響信任」標示。
4. **少看的說明與收起規則**：為什麼是少看、空白欄位不收起、收起的區塊。
5. **今天改為收件匣**：分組與排序、信任一覽。
6. **信任時間軸**：圓點、層級帶、層級事件（資料已有）。
7. **員工卡**：職務圖示、交件與來源、最近 10 次圓點。
8. **交辦表單**：選員工自動帶入來源、結果說明、交辦清單。
9. **工作帳本**：表格、事件篩選、層級改變的灰底列。
10. **手機**：子頁按鈕列、驗收底部固定按鈕。
11. （需要決定後才做）重點在全文中的標記格式。

每張 Issue 的驗收條件可直接引用第 4、6 節的規格與 `screens/` 的對應畫面。

## 10. 待決問題

1. 重點在全文中的標記格式（第 8 節）。
2. 「AI」標記的寫法：等寬「AI」框，或改成較柔和的「AI 員工」文字。
3. 公開原型要不要另外提供以「今天」為首頁的入口給個人經營者（牽動 ADR 0004，建議放到第 1 階段後）。
4. Dark 模式：v3 只做了 Light；Dark 依 ADR 0008 共用 token，時間軸的少看層級帶與 `danger` 細框需要確認對比。
5. 英文版的版面與文案（`docs/design.md`「英文版面」）。
